# 2-builtin-tools-reference

Snow App ships with a set of built-in MCP tools that let the AI agent perform file operations, terminal commands, web search, browser automation, and more. This article lists all built-in servers and tools.

## 1. Tool Naming Convention

Built-in tool full names follow the pattern `{server-id}-{tool-name}`, e.g. `filesystem-read`. Some server IDs contain `-` (e.g. `user-interaction`); when resolving the tool name, the built-in server list is used for **longest-prefix matching** to disambiguate.

### bash

| Full tool name          | Purpose                                                           | Key parameters                                                                                  |
| ----------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `bash-terminal-execute` | Execute terminal commands (build, test, package management, etc.) | `command`, `description`, `workingDirectory`, `timeout`, `detach`, `isInteractive`, `sessionId` |

> **Shell source**: Commands ALWAYS run in the shell configured in Terminal
> settings; when unset, the auto-detected default terminal is used (Windows:
> PowerShell → CMD → Git Bash → COMSPEC). This tool does not accept a
> `shellPath` parameter — use `terminal-open` to open an interactive
> terminal with a specific shell.

> **Warm shell**: on the PowerShell family (pwsh / Windows PowerShell) consecutive
> commands reuse one persistent warm shell session, so they no longer pay a fresh
> shell cold start (measured: ~400ms → ~40ms per trivial command). The working
> directory is still reset for every command, while process-level state
> (environment variables, `$global:` variables) persists between commands like in
> an interactive terminal; commands that read stdin (`Read-Host`, password
> prompts) must pass `isInteractive:true`. `detach` and `isInteractive` still run
> as one-shot processes.

> **Working directory**: `workingDirectory` may be omitted — it then defaults to
> the current project's workspace directory (the remote workspace path for SSH
> projects). It is only mandatory when the session is not bound to a project
> workspace.

### grep

| Full tool name | Purpose                           | Key parameters                                                                         |
| -------------- | --------------------------------- | -------------------------------------------------------------------------------------- |
| `grep-search`  | Search file contents with ripgrep | `pattern`, `description`, `path`, `fileGlob`, `caseSensitive`, `isRegex`, `maxResults` |
| `grep-find`    | Find file paths by glob pattern   | `pattern`, `description`, `path`, `maxResults`, `searchAll`                            |

> **Explanation**: `description` lets users skip decoding the regex — the model
> writes one sentence (in the user's language) describing what the search looks
> for, and the UI shows it in place of the raw regex (the regex itself stays
> visible in the card). When the model omits it the card just falls back to the
> regex — the search still runs.

> **Glob semantics**: a `grep-find` `pattern` without `/` matches file names at
> any depth (e.g. `*.ts`); with `/` it matches the path relative to the search
> root (e.g. `src/**/*.{ts,tsx}`). Results contain file paths only.
>
> **Filtering vs. exhaustive search**: heavy directories (`node_modules`,
> `.git`, `target`, `dist`, ...) are skipped by default (the ripgrep backend also
> honors `.gitignore`); set `searchAll: true` to disable those filters for an
> exhaustive search (noticeably slower on large repositories).

#### Frame targeting and trust boundaries

- `browser-frames {instanceId?}` enumerates the guest's main and child frames, returning opaque document-scoped `frameId`, `parentFrameId`, `isMainFrame`, and redacted `url`/`name`. These are not CDP frame/session IDs.
- Optional `frameId` is supported by evaluate, get_tab_content, wait, click, type, hover, select_option, upload-file, scroll, press_key, get_css_styles and audit, and by devtools snapshot/ax/console/network. press_key goes to the frame's currently focused element; scroll and get_css_styles refs use that frame's AX snapshot; audit runs axe/SEO/best-practice checks against the target frame document only and counts console errors for that frame. console/network return only that frame's CDP records (frame-filtered console omits Log entries without frame attribution), and fallback data without frame attribution fails explicitly. Omission selects the main frame. Re-enumerate after navigation/reload/detachment or guest recreation. A stale ID raises `FRAME_STALE`; it never falls back to the main frame.
- Frame scripts, text and waits (including the main frame when frameId is omitted) execute via main-process `WebFrameMain.executeJavaScript`. AX, refs, uploads and real input use a matched CDP context/session. OOPIFs are attached only for iframe targets descended from this guest. Frame target sessions are held by a shared manager and released when the debugger detaches (including DevTools contention) or the guest is destroyed; object handles are released per operation, and a validated document's CDP target is reused until that document is replaced. Network/Fetch/Console/Dialog events are captured and answered per frame session; network detail keys, console `cdpFrameId` and dialog `frame` distinguish the main frame from iframes, OOPIF Log entries are attributed to their target frame, and root-session Log entries without frame attribution keep no `cdpFrameId`. Dialog listings return `dialogId`; a response may target one dialog with `dialogId`, otherwise the same response applies to every pending dialog. For actions with frameId, expect is evaluated in the target frame while URL/title/loading/events stay top-level and snapshot text comes from the target frame. A missing session fails explicitly without main-frame fallback. No authentication tickets are copied and no cookies/authentication storage are read by the frame implementation.
- Frame AX `fr-...` refs belong only to that frame's latest snapshot; use the original frameId with click/type/hover/select/upload refs. Re-snapshot invalidates previous refs. Input values are omitted even in verbose frame AX. Legacy main-frame ref behavior is unchanged.
- URL userinfo, query, fragment and sensitive path segments are removed/masked. The common tool result boundary recursively redacts credential keys, Bearer/JWT and credential-shaped text; PNG binary is preserved only for screenshots. Do not evaluate authentication data. Keyword checks and output redaction are not an arbitrary-JavaScript sandbox and cannot identify every custom short-string secret.
- Pointer coordinates are translated through each frame owner and checked for occlusion. Rotated, skewed, mirrored and perspective frames are explicitly rejected rather than approximately clicked. webSecurity remains enabled; unavailable frames/CDP contexts or DevTools contention fail explicitly.
- Packaging uses Electron 37.10.3. This describes the implementation contract, not runtime acceptance of every real site, sandbox iframe, OOPIF, CSS transform or platform combination. Timeouts do not terminate arbitrary page JavaScript; avoid long-running/infinite-loop expressions.

### sub-agents

| Tool name                  | Purpose                                                                                                                                                                                                                                                                                        | Key parameters                               |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `sub-agents-activate`      | Activate a sub-agent to run a task independently (the required `summary` becomes the sub-agent conversation's title/summary in the sidebar list); optional `acceptance` attaches an acceptance checklist                                                                                       | `agentId`, `summary`, `prompt`, `acceptance` |
| `sub-agents-listTeammates` | Query the sub-agents **currently running** in the same conversation session (only teammates of the same session are visible)                                                                                                                                                                   | —                                            |
| `sub-agents-sendMessage`   | Send a message to a teammate sub-agent still running in the same session; delivered as a Pending message at the end of the target's current round, prefixed with the sender's identity                                                                                                         | `conversationId`, `message`                  |
| `sub-agents-listSubAgents` | List the current session's sub-agents (including those already finished during this app run), returning `status` (running/completed/failed/cancelled), `resumable` and the acceptance snapshot (per-item status/evidence/`satisfied`)                                                          | —                                            |
| `sub-agents-continue`      | Send a message to a sub-agent of the current session and resume it: finished targets are reactivated with their original configuration (model/tools/system prompt) and full history; still-running targets get a queued Pending message; optional `acceptance` adds or refines checklist items | `conversationId`, `message`, `acceptance`    |

`agentId` must be chosen from the sub-agent list injected into the main session's system prompt (the built-in `agent_general` is a generic fallback); when in doubt, query `config-list` (scope=`subAgents`) first.

**Optional acceptance checklist and evidence receipt**: `sub-agents-activate` accepts `acceptance: [{ id, description, required? }]` (at most 20 items; `required` defaults to true). With a checklist, every tool result the sub-agent receives is prefixed with a host-assigned evidence id (`[evidence ev-N]`), and the sub-agent must end its final answer with an `acceptance` fenced block reporting each item's `status` (completed/incomplete/blocked/unverified), `observation`, `evidence` (evidence ids) and `reason`. At finalization the host validates each cited id against the real tool execution log of that sub-agent conversation: `completed` without valid evidence is downgraded to `unverified`, unreported items stay `unverified`, and nothing is ever treated as passed by default; the report block is removed from the summary returned to the main agent. Tool results return `acceptance` (per-item status, trimmed evidence previews, `satisfied`) plus `acceptanceSatisfied`; `satisfied` is true only when every required item is completed with valid evidence, otherwise an `instruction` asks the main agent to continue the same sub-agent for the missing items. Valid evidence proves the cited call happened, not that the item is correct — the main agent still judges whether it supports the conclusion. `sub-agents-continue` also accepts `acceptance` to add or refine checklist items; recorded statuses are preserved, so a follow-up only updates the unfinished items (no need to repeat completed steps). Tasks without a checklist behave exactly as before (no evidence markers, no receipt fields). The checklist and evidence log are runtime state of this app run: they are not restored after a restart, so pass the checklist again on `continue`.

Same-session communication is bounded by **session isolation**: `listTeammates` never exposes sub-agents of other conversations, and cross-session `sendMessage` / `continue` calls are rejected. After an app restart, sub-agent sessions can be resumed and continued (see [5-configure-hooks-and-subagents](../2-guides/5-configure-hooks-and-subagents.md)).

| `lsp-workspace-symbols`     | Workspace Symbol Search          | `query`; optional `workspaceRoot`                                                    |

**Scope:** symbol-capable tools also accept optional `workspaceRoot` when resolving without `filePath`. It must be an existing absolute local directory; relative paths, files and SSH are rejected. The current project root is used when omitted; if no reliable root exists, provide one explicitly. It neither grants project/whitelist permissions nor searches every project.

**Result safety:** internal addressing checks complete candidates before deciding uniqueness; a display cap cannot establish uniqueness. Warnings, incompleteness, partial/failed and `partial_symbol_search` do not mean “no problems/only one target.” Without a verified `selectionRange`, candidate ranges are navigation hints with `requiresExplicitCoordinates`; do not use a flat range start as rename coordinates. The UI exposes completeness/warnings; process running is not index readiness.

**Freshness:** `ensure_open` compares actual full text and sends didOpen/didChange; workspace requests synchronize opened documents and close deleted ones. Diagnostics no longer read or write persistent `lsp_diagnostic_cache` results; this change does not delete the old table/data. Re-diagnosis cost is accepted rather than allowing single-file mtime/size to hide dependency/configuration changes.

The ID `lsp-workspace-symbols` is unchanged. Labels are `全局符号搜索` / `全域符號搜尋` / `Workspace Symbol Search`. <!-- docs-check: allow-cjk -->

The former `lsp-definition`, `lsp-type-definition` and `lsp-implementation` tools are merged into `lsp-goto{kind}`. See [LSP design](../4-architecture-and-development/7-lsp-external-language-server-design.md) for current behavior and the pending acceptance matrix.

#### Invocation and result contracts (2026-09-26)

- **Conditional MUST:** semantic tasks must use LSP when the corresponding tool is visible and supports the target language/operation. Explain disabled, unauthorized, uncovered, backed-off or unhealthy cases and use visible fallbacks without expanding permissions.
- **Strict input:** diagnostics requires `filePaths` (1..30); `symbols` requires `filePaths` (1..10); `hover` / `goto` require `items` (1..10 each); `references` requires `items` (1..5). Even a single target must be sent as a one-element array; single-target parameters are no longer accepted. Missing arrays, wrong types, empty arrays/entries and oversized lists are rejected without silent truncation. File paths are deduplicated by physical identity, preserving first occurrence.
- **Stable output:** all these operations return a `batch:true` envelope (`files` or `items`) with aggregate status/counts and per-target results. Each target retains complete/partial/failed/ambiguous status plus its errors or warnings. Ambiguous, failed or partial items must never be reported as overall complete. `lsp-rename` remains a single-symbol operation and keeps its preview-capability/partial-application contract.
- **Bounded execution:** read-only batch tasks use target concurrency 3 and preserve input order. Reference/outline totals must not count failed or incomplete items as successful.
- **Preview capability:** `dryRun=true` returns `previewId/previewExpiresAt`; 5-minute TTL, at most 32 per session, single-use and content-bound. `dryRun=false` requires the capability plus write authorization. Changed contents, expiry or consumption require another preview; never display the raw value or automatically apply.
- **Partial application:** multi-file writes are not transactional. Inspect `appliedFiles`, `failedFile`, `failedFileMayBeModified`, `error` and `requiresNewPreview`. Written files are not automatically rolled back; never replay the old capability.

Both label families use the 11 semantic names above, preserving IDs/historical keys. Goto may specialize to Go to Definition / Go to Type Definition / Find Implementations by kind. Read-only batches are capped at concurrency 3 and preserve input order; see [LSP design §0.7](../4-architecture-and-development/7-lsp-external-language-server-design.md) for the current contract. This reference does not claim live language-server runtime acceptance.

| Full tool name             | Purpose                                                                                                                                                                                                                                                                                                                                                                | Key parameters                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `app-control-setMode`      | Enable/disable Goal Mode or WorkTree Mode                                                                                                                                                                                                                                                                                                                              | `mode`, `enabled`                                        |
| `app-control-openSettings` | Open the specified settings page                                                                                                                                                                                                                                                                                                                                       | `page`                                                   |
| `app-control-conversation` | Conversation operations in the current project, dispatched by `action`: `create` creates a conversation (optional `text` writes an initial user message; `autoReply=true` starts one turn); `send` delivers a user message to a top-level conversation (starts when idle, queues when busy); `activate` switches the UI to a conversation. Not available to sub-agents | `action`; `title`, `text`, `autoReply`, `conversationId` |

Memos, site-blocking rules, scheduled task creation, and project creation moved into the `config` tools; app-control no longer provides those tools:

- memos: the `memos` scope;
- site-blocking rules: read with `config-get scope=appSettings key=blockedPatterns`, write with `config-set scope=appSettings key=blockedPatterns`;
- new scheduled task: `config-set scope=scheduledTasks key="new"`;
- new project: `config-set scope=workspace key=directories value={action:"create", name, parentPath?}`.

Site-blocking rules are the app-global `proxy_browser_settings.blockedPatterns`, not project configuration. The written `value` may be an array (full replace), or `{add: [...]}` / `{remove: [...]}` / `{replace: [...]}`. The Renderer validates rules with JavaScript `RegExp`; `add` removes exact duplicates while preserving order, `remove` deletes exact strings, and `replace` fully replaces the list. Matching rules filter `websearch` results and cause `websearch-fetch` to refuse a fetch.

The `value` of `config-set scope=scheduledTasks key="new"` is `{name, prompt, schedule, id?, preScript?, preScriptTimeoutMs?, runOnScriptError?, apiProfile?, model?, basicModel?, thinkingStrength?}`; the full field contract is the `createGuidance` returned by `config-list scope=scheduledTasks`. The model fields follow these rules:

- `model` pins the advanced model for the task's main requests. When `apiProfile` is specified but `model` is omitted, Snow uses only that same profile's `advancedModel`; it does not borrow the current conversation's model or a model from another profile;
- `basicModel` overrides only the first conversation title's model. When omitted, the task conversation's bound profile supplies `basicModel`; it does not affect main requests;
- an omitted or trim-empty `thinkingStrength` stores no snapshot, so the task inherits the selected profile's latest setting when it fires;
- these fields are explicit overrides or profile defaults. Snow App does not switch basic/advanced models based on prompt complexity, and the two model classes do not fall back to each other.

### config-logs-read

| Full tool name     | Purpose                                                                                                                            | Key parameters                                             |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `config-logs-read` | Read current-conversation Snow App SQLite logs, including bounded/redacted API request and response bodies; excludes Snow CLI logs | `level`, `module`, time range, `limit` (max 100), `offset` |

This tool is **disabled by default**; enable it per project in the MCP panel before the model can see it.

`items`, `total`, and `hasMore` remain scoped to the current conversation. Details return log metadata and bounded context/error; API records additionally return bounded `requestBody` / `responseBody` fields. Before persistence, the logger redacts sensitive-name fields and exact occurrences of the active API key; request headers are not logged. This cannot guarantee detection of every credential format, so review details before sharing. `systemSummary` returns application-wide counts under the same level/module/time filters, without pagination: total, unassociated-row count, fixed main/renderer source counts and four log-level counts. It returns no identifiers, text, context/errors or payloads from other conversations or unassociated rows. Rows without a conversation ID may be new system logs; they contribute only to the summary, never details. If current-conversation `total=0`, compare `systemSummary.total`. Empty/whitespace optional string filters mean omitted.

> **`apiProfiles` model fields and activation constraints**: `advancedModel` is a
> profile's default advanced model (ordinary conversations still use their selected
> model), while `basicModel` serves conversation titles, AI Commit, `@?` file search,
> and codebase Agent Review. Snow App does not switch between them based on prompt
> complexity, and they never fall back to each other. `config-set` uses merge
> semantics. A merged profile with `isActive: true`—whether created active or
> activated later—requires both `advancedModel` and `basicModel` to be non-empty
> after trim. An inactive profile may remain an incomplete draft; API-key presence
> is not part of this model-completeness check.
>
> **Safety mechanism (config-change protection)**: to prevent AI from
> accidentally modifying/deleting user configuration, the config tool
> enforces the following constraints —
>
> - **Delete confirmation**: `config-delete` must first be confirmed by the
>   user (`askUserQuestion`) and then called with `confirmed: true`; anything
>   else is rejected. `imagegen` delete **clears all channels** (not a single
>   key), so extra care is required.
> - **Pre-write backup**: `config-set` / `config-delete` automatically back up
>   the current value to `~/.snow/.config-backups/` before writing (both
>   file-backed and DB-backed scopes), as a temporary safety net during the
>   write; **the backup is removed after a successful verified write**, with a
>   per-file cap of 10 backups as a fallback for leftovers.
>
> **Structural validation**: `settings.codebase`, `custom-headers.schemes`,
> `system-prompt.prompts` and `lsp-config.servers` are deeply validated on
> write (known fields are type-checked one by one, e.g.
> `codebase.embedding.dimensions` must be a number) so an agent cannot corrupt
> nested fields; unknown fields are allowed through for forward compatibility.
>
> **Project-scoped settings**: passing `projectId` to the `settings` scope's
> `mcpServers` / `sensitiveCommands` reads/writes **project-level** config
> (app database, takes effect immediately, same source as the UI project
> settings): `mcpServers` is a full replace (value is
> `{name: {type,url,command,args,env,headers,enabled,timeoutMs}}`);
> `sensitiveCommands` is a full replace (value is an array of
> `{commandId, pattern, description, enabled}`; a commandId matching a global
> rule becomes an enabled override, others become project custom rules);
> all other keys reject `projectId` with a clear error.

### memory

| Full tool name  | Purpose                                                                                                  | Key parameters                                                                           |
| --------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `memory-save`   | Save a cross-session project memory (same-title saves merge)                                             | `title`, `content`, `kind`, `importance`, `tags`, `sessionId`                            |
| `memory-search` | Search project memories by keywords (score-ranked)                                                       | `query`, `kind`, `status`, `limit`                                                       |
| `memory-list`   | Browse project memories page by page                                                                     | `status`, `kind`, `limit`, `offset`                                                      |
| `memory-update` | Update a memory entry (omitted fields keep their values)                                                 | `memoryId` (string or array), `title`, `content`, `kind`, `importance`, `status`, `tags` |
| `memory-delete` | Delete memories (**DESTRUCTIVE**, requires user approval); `memoryId` may be an array for batch deletion | `memoryId` (string or array), `confirmed`                                                |

> **Project isolation & injection**: every memory tool reads/writes scoped to
> the current conversation's project (`directory_id`) — the model cannot cross
> projects; the project context is injected by the call chain, so tools take
> no projectId parameter. The main session's system prompt automatically gets
> a trailing `## Project Memory` section: active entries with
> `importance >= 3` are injected top-first (capped at 30 entries / 4000
> chars), and the section tail carries the current conversation id, guiding
> `memory-save` to pass it as `sessionId` (the per-conversation provenance
> anchor). An empty bank gets a short bootstrap hint instead. Sub-agents do
> not receive the section.
>
> The section is frozen per conversation: it is rendered on the first request
> and stored as a snapshot (`memory_prompt_snapshots` table), then reused
> verbatim on every later turn — saving or editing memories mid-session never
> changes the prompt prefix already sent, so the conversation's prompt cache
> keeps hitting and new memories only take effect in conversations started
> afterwards (use `memory-search` for the latest state in the running
> session).
>
> When a conversation is deleted, the confirm dialog counts the memories saved
> from it and lets the user choose whether to delete them as well (kept by
> default); its injected snapshot always goes away with the conversation.
>
> `memory-delete` is destructive: obtain the user's explicit approval via
> `user-interaction-askUserQuestion` first, then retry with `confirmed: true`;
> calls without it are rejected.
>
> `memoryId` accepts a string or an array. `memory-delete` with an array needs one confirmation for the whole batch. `memory-update` with an array applies the same `kind` / `importance` / `status` / `tags` patch to every entry, all-or-nothing; `title` and `content` may only change for a single entry because the title is the dedup key.
>
> **User-facing entries**: the memory bank opened from the sidebar "Project
> Memory" entry supports keyword search (title / tags / content, reusing the
> `memory-search` ranking, stackable with the status / kind filters, with
> matches highlighted); typing `/memory` in chat lists the memories the current
> conversation (including its sub-agents and WorkFlow nodes) saved or merged,
> with full content on expand and a jump that locates an entry in the memory
> bank.

### decision

| Full tool name      | Purpose                                                                                                                                                                                                                | Key parameters                                                    |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `decision-evaluate` | Ask the decision model typed questions about evidence and get structured answers: predicate returns a probability, choice the option plus per-option probabilities, score the value, level and per-level probabilities | `questions` (required), `evidence` (required), `model` (optional) |

Parameters:

| Parameter                            | Description                                                                                                              |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| `questions[].name`                   | Question id (letters, digits, `_`, `-`, at most 64 characters, unique); answers are keyed by it                          |
| `questions[].type`                   | `predicate` / `choice` / `score`                                                                                         |
| `questions[].choices`                | choice only: 2-50 `{value, description?}` entries                                                                        |
| `questions[].levels`                 | score only: 2-10 `{label, description?}` entries, lowest first                                                           |
| `questions[].whenTrue` / `whenFalse` | predicate only, optional: what counts as true / false                                                                    |
| `questions[].images`                 | Question-level image paths, sent only with that question (for example one candidate per question)                        |
| `evidence.text`                      | Plain-text evidence                                                                                                      |
| `evidence.json`                      | Structured evidence (a real JSON value)                                                                                  |
| `evidence.images`                    | Image paths shared by all questions (for example a screenshot or a reference image)                                      |
| `model`                              | Decision model id or name; omitted means the **default model for the decision tool** in Settings > API > Decision models |

> **Image evidence**: PNG / JPEG only (detected from the file header), at most
> 16 MiB per file and 16 distinct images per call, 24 MiB in total after
> processing; images whose long edge exceeds 1568 px are downscaled before
> sending. Paths may be absolute, relative to the project root, or `upload/...`,
> and must stay inside the project workspace (linked projects included; the bound
> worktree in WorkTree mode), the app data directory, the image library or the
> system temp directory. An unreadable, unsupported, oversized or out-of-scope
> image fails the whole call with its path and **nothing is sent**; images are
> read and sent only when this tool is called explicitly.
>
> **Both providers support images**: OpenAI Decisions uses `input_image`
> (shared evidence in `input`; question-level images turn `instructions` into an
> `input_text` + `input_image` array). An endpoint that only speaks the
> pre-GA protocol rejects that array with a 400; the request then falls back to
> a compatible form — question-level images move into the shared `input` labelled
> `Image for question "<name>" (<file>)`, and the question's instructions point
> at those labels — and that endpoint keeps using that form. TypeSafe Jev (1.13
> and later) uses the top-level `assets` map with reference strings, and the
> `TypeSafe-Danger-Zone-Images: true` header is sent automatically. Jev also
> requires both sides of an image to be at least 280 px; smaller images are
> rejected locally. A refused question returns `refused: true` while the other
> questions still get answers.
>
> The tool sends local evidence to an external decision model API, so it is not
> on the read-only auto-approval list.
