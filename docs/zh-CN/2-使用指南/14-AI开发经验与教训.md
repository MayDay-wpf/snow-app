# 14-AI 开发经验与教训（Lessons from Production AI Development）

> 从互联网权威来源（Anthropic 官方工程博客/文档等）与真实项目实践中提炼的
> AI Agent 开发经验教训。平台中立——不依赖 Trellis 或任何特定框架，Snow App
> 内置工具即可执行。每节标注来源，供深入阅读。

---

## 1. 怎么确定需求（Requirements）

**核心教训：让 AI 采访你，而不是你一次性讲完。**

- **Interview 模式**（Anthropic 官方推荐）：给 AI 一个简短描述，让它用
  `user-interaction-askUserQuestion` 逐题采访你——技术实现、UI/UX、边界情况、
  取舍权衡，直到覆盖所有难点，然后写完整 spec
- **spec 要自包含**：命名涉及的文件与接口、明确"范围外"（out of scope）、
  以"端到端验证步骤"结尾——"写 spec 花的时间比盯实现更值"
- **验收标准先行**："完成"的定义必须在动手前明确（可运行的验证命令/测试），
  否则 AI 只能靠"看起来完成了"停手，错误全靠你事后发现
- **模糊 prompt 也有用**：探索阶段"你会怎么改进这个文件？"能带出你没想到的问题；
  但一旦进入实现，必须具体（指名文件、场景、测试偏好）

> 来源：Anthropic《Best practices for Claude Code》"Let Claude interview you"；
> 我们的经验：需求不清直接开写 = 返工的最大来源。

## 2. 怎么开发（Development）

**核心教训：先探索，再计划，后编码——避免解决错误的问题。**

- **四阶段**：Explore（只读探索）→ Plan（写出详细计划，可编辑）→
  Implement（按计划实现，对照验证）→ Commit（描述性提交 + PR）
- **小改动跳过计划**：能一句话描述 diff 的改动（改 typo、加日志、重命名变量）
  直接做；跨多文件/不熟悉代码/方案不确定时才值得计划
- **Prompt 要具体**：
  - 限定范围：指名文件、场景、测试偏好（"避免 mock"）
  - 指向来源："看 ExecutionFactory 的 git 历史，总结 API 怎么来的"
  - 引用现有模式："参考 HotDogWidget 的实现模式做新组件"
  - 描述症状 + 期望："登录超时后失败，查 src/auth 的 token refresh，
    先写失败测试再修"
- **上下文是最稀缺资源**：会话窗口填满后性能下降、开始"忘事"。任务之间
  `/clear`；探索交给子代理（独立上下文）；把长期规则写进 CLAUDE.md/AGENTS.md
  这类每会话加载的文件（保持精简，过长会被忽略）
- **CLAUDE.md/AGENTS.md 写作**：只放 AI 猜不出来的（bash 命令、风格差异、
  测试偏好、仓库礼仪、架构决策、环境怪癖）；"删掉这行 AI 会不会犯错？"
  不会就删；定期修剪（规则失效/过长 = AI 忽略）

> 来源：Anthropic《Best practices》"Explore first, then plan, then code"、
> "Provide specific context"、"Write an effective CLAUDE.md"。

## 3. Debug / 修 Bug（Debugging）

**核心教训：给 AI 一个它能运行的"检查"，反馈循环自己闭合。**

- **验证优先于一切**："看不出完成"和"检查通过"是天壤之别——给 AI 测试、
  构建退出码、lint、diff 脚本、截图对比，它就能自己迭代到绿
- **修根因不修症状**："构建失败"要贴错误 + 要求"修根因，别压制错误"
- **常见调试配方**（Anthropic Common Workflows）：
  1. 贴错误信息 → 2. 要求修复建议（几个方案）→ 3. 应用修复 → 4. 重跑验证
  - 告诉 AI 复现命令和堆栈；说明错误是间歇性还是持续
- **展示证据而非声称成功**：要求 AI 附测试输出/命令结果/截图——审查证据比
  自己重跑快，且对无人值守会话有效
- **多智能体调试**（Anthropic 生产经验）：agent 每次运行结果不同（非确定性），
  "找不到明显信息"这类问题必须靠**全链路 tracing** 才能看到 agent 的搜索词、
  选了哪些来源、工具是否失败——高层面板监控决策模式，不监控对话内容
- **错误会复合**：agent 系统中小故障会让 agent 走上完全不同的轨迹——
  需要可恢复设计（checkpoint + 从断点续跑，而不是从头重启）

> 来源：Anthropic《Best practices》"Give Claude a way to verify its work"；
> 《Common workflows》"Fix bugs efficiently"；《Multi-agent research system》
> "Debugging benefits from new approaches"。

## 4. 怎么测试功能（Testing）

**核心教训：测试不是"写完补"，是验证循环的一部分——先给 AI 验收标准。**

- **先定验收再实现**：实现前给出示例测试（"user@example.com 为 true，
  user@.com 为 false，实现后跑测试"）——AI 会照着写并自测
- **让 AI 按现有模式写测试**：先看已有测试文件，匹配风格/框架/断言模式；
  要求覆盖边界条件（错误输入、边界值、意外输入）
- **AI 生成测试的三种用法**（Anthropic Common Workflows）：
  1. 找出未覆盖代码 → 2. 生成脚手架 → 3. 补边界用例 → 4. 跑 + 修失败
- **多智能体评估经验**（Anthropic）：
  - **立刻开始小样本评估**：20 个真实用例就能看出 prompt 改动效果
    （早期改动收益巨大：30%→80%）；别等"几百用例的完整 eval"
  - **LLM-as-judge 可规模化**：单次 LLM 调用按 rubric 打分（事实准确性/
    引用/完整性/来源质量/工具效率）0.0-1.0 + pass/fail
  - **人工测试不可替代**：人类发现 eval 漏掉的边界（如早期 agent 总选
    SEO 农场而非权威源——加"来源质量启发式"修复）
  - **端状态评估**：对多轮修改状态的 agent，评"最终状态对不对"而非
    "每一步对不对"（agent 会走不同的有效路径）

> 来源：Anthropic《Best practices》"Give Claude a way to verify its work"；
> 《Common workflows》"Work with tests"；《Multi-agent》"Effective evaluation"。

## 5. 怎么上线（Deployment）

**核心教训：agent 系统是"有状态、几乎连续运行"的网，不能整批替换。**

- **彩虹部署（Rainbow deployment）**：agent 可能处于流程任意位置，不能同时
  更新所有实例——新旧版本同时运行，流量逐步迁移，避免更新破坏运行中的 agent
- **状态与恢复**：agent 长时间运行、跨多次工具调用持有状态——错误不能从头
  重启（昂贵且恼人），要能**从断点恢复**；重试逻辑 + 定期 checkpoint +
  让 agent 感知工具失败并自行适应
- **原型到生产的差距比想象大**："能在开发机跑"和"可靠的生产系统"之间的
  工程量大得多——最后一段路往往占整个旅程的大半

> 来源：Anthropic《Multi-agent research system》"Deployment needs careful
> coordination"、"Production reliability"。

## 6. 怎么运维（Operations）

**核心教训：可观测性是 agent 系统运维的第一公民。**

- **标准可观测性 + agent 决策监控**：除常规日志/指标外，监控 agent 的
  决策模式与交互结构（搜索词、来源选择、工具使用）——不监控对话内容以
  保护隐私
- **tracing 是 debug 的前提**：没有全链路 trace，你无法回答"agent 为什么
  没找到明显信息"（坏查询？差来源？工具失败？）
- **定时任务要写清楚成功标准**：无人值守任务无法提问——"成功长什么样、
  结果怎么处理"必须写进 prompt
- **工具描述质量决定成败**：Anthropic 的 tool-testing agent 用几十次测试
  打磨工具描述，使后续 agent 任务时间下降 40%——坏描述会把 agent 带进
  完全错误的路径

> 来源：Anthropic《Multi-agent》"Production reliability and engineering
> challenges"；《Best practices》"Run Claude on a schedule"。

## 7. 多智能体协作（Multi-Agent）

**核心教训：并行 + 独立上下文 = 大规模扩展，但要会分工、控成本。**

- **为什么有效**：token 用量解释 80% 的性能差异——多 agent 用独立上下文
  并行消耗更多 token = 更强的搜索/推理能力；内部评测中
  lead=Opus + subagent=Sonnet 比单 Opus 高 90.2%
- **代价**：agent 约用 4× 聊天的 token，多 agent 约 15×——只在任务价值
  足够高时用（重度并行、超单上下文容量、多复杂工具）
- **教编排者如何委派**：每个子代理要有目标、输出格式、工具/来源指引、
  明确边界——否则子代理重复劳动或漏活（示例：3 个子代理重复调研同一话题）
- **工作量匹配复杂度**：简单事实查询 1 个 agent 3-10 次调用；直接比较
  2-4 个子代理各 10-15 次；复杂研究 10+ 子代理分工——防止为简单查询过度投资
- **先宽后窄**：搜索先短宽查询，评估可用内容，再逐步收窄（agent 默认会
  用过长过具体的查询）
- **产出落盘避免"传话游戏"**：子代理把结构化产出写入文件系统，给协调者
  传轻量引用——比通过对话历史复制大输出更保真、更省 token
- **并行工具调用**：lead 一次起 3-5 个子代理 + 子代理 3+ 工具并行 →
  复杂查询时间降 90%
- **适用边界**：需要共享上下文或 agent 间强依赖的任务不适合多 agent；
  大多数编码任务的并行度低于研究

> 来源：Anthropic《Multi-agent research system》全文。

## 8. OpenAI 的经验教训（Agents SDK / 编排 / 护栏 / 评估）

**核心教训：先单 agent，契约变了再加专家；护栏放对位置；评估是持续过程。**

### 8.1 编排：Handoff vs Agents-as-tools

- **先决定"谁拥有最终回答"**：每个分支都要明确——专家接管对话（handoff）
  还是经理保持控制、专家只做有界工具（agents-as-tools）
- **handoff 适用**：该分支需要专家完全接管（不同指令/工具/策略）
- **agents-as-tools 适用**：经理要综合最终答案；专家做有界任务（摘要/分类）；
  想要一个稳定的外层工作流 + 内嵌专家调用
- **专家面保持清晰**：每个专家职责收窄；`handoffDescription` 短而具体
- **不要过早拆分**：能单 agent 就单 agent——只有能力隔离、策略隔离、prompt
  清晰度或 trace 可读性实质性改善时才加专家（过早拆分 = 更多 prompt、更多
  trace、更多审批面，工作流未必更好）

### 8.2 护栏（Guardrails）与人工审查

- **三层护栏**：input（主模型跑前拦截非法请求）、output（输出离开系统前
  校验/脱敏）、tool（函数工具参数/结果检查）——**放对位置**：input 只跑
  链上第一个 agent，output 只跑产出最终输出的 agent，tool 只跑它所挂的工具；
  经理式工作流别只靠 agent 级护栏，要把校验放在产生副作用的工具旁边
- **人工审查（human-in-the-loop）**：副作用操作（取消订单/编辑/shell/
  敏感 MCP 动作）用 `needsApproval` 暂停运行——模型仍可决定需要动作，
  但运行暂停直到人批准/拒绝
- **审批生命周期**：记录 interruption + 可恢复 state → 应用批准/拒绝 →
  从 state 恢复同一 run（不是新会话）；审查耗时长就序列化 state 存起来，
  稍后恢复——"仍然是同一个 run"

### 8.3 评估（Evals）——OpenAI 视角

- **eval-driven development**：尽早且频繁评估，每个阶段写范围化测试
- **任务专属评估**：测试要反映真实生产分布（用生产数据 + 领域专家数据 +
  历史日志）；覆盖典型、边界、对抗三类用例
- **全部打日志**：开发时就记录，之后从日志挖好的 eval 用例
- **自动评分 + 人工校准**：结构化评估以便自动打分；用人类反馈校准
  自动评分（保持一致性）
- **反模式**：只靠学术指标（perplexity/BLEU）；数据集不忠实复现生产流量；
  "看起来能用"式评估或上线前才补 eval；忽略人工反馈
- **LLM 擅长判别而非生成**：评估应聚焦成对比较、分类、按标准打分，
  而非开放式生成——更可靠
- **在非确定性进入系统的地方加 eval**：单轮交互 → 工作流 → 单 agent →
  多 agent，复杂度越高非确定性点越多

> 来源：OpenAI《Agents SDK》Orchestration and handoffs / Guardrails and human
> review / Evaluation best practices。

## 9. Cursor 的经验教训（自主性管控 / 云端智能体）

**核心教训：自主性是个旋钮不是开关；环境即产品；持久执行与解耦。**

### 9.1 自主性管控（Auto-review 分类器）

- **不要非开即关**：反复请求许可本身有安全风险（提示多了人们不再认真读，
  批准流程失去意义）——低风险自由行动，跨关键边界才放慢
- **分类器模式**：小模型 + 足够推理能力做"操作前审查"（快、准、便宜）；
  低推理模型不一定更快——理解不了策略时反而花更多时间/ token
- **上下文判断风险**：同一条命令在不同工作流中风险不同——判断"操作与
  用户请求的关系"和"判断错误的后果"
- **分类器也可用工具**：`python script.py` 安不安全取决于文件内容——先
  ReadFile/Grep/Glob 检查工作区再裁决
- **拦截 ≠ 打断用户**：分类器把原因反馈给父 agent，父 agent 通常能换条
  更安全路径继续（实测拦截约 4% 操作，仅约 7% 对话最终打断用户；对比
  某些企业客户此前约 40% 操作被拦截）
- **评估分类器**：内部会话数据（约 12 小时 → 6,122 行带标签）+ 合成数据
  （覆盖最糟糕情况：读密钥/碰生产数据/不可信指令/大副作用）；策略变化时
  要重新标注（否则测的是过时的问题定义）；查找结果反复波动（6 次放行
  4 次拦截 = 策略或 prompt 定义不充分）

### 9.2 云端智能体

- **开发环境本身就是产品**：影响输出质量的首要因素是完整开发环境（本地
  继承现成环境，云端要重建）；缺失时往往没有报错，只是输出质量轻微下降，
  容易被误归因于模型——检查环境先于怀疑模型
- **长时间运行需要持久执行**：work-stealing 架构早期只有 1 个 9 可靠性；
  迁移到 Temporal（重试/跨机器调度/跨故障持久性）后 >2 个 9，每天处理
  5000 万+ action；从"永久"工作流转向"完成任务就退出"的短工作流让升级
  更容易
- **智能体 / 机器 / 会话状态解耦**：agent 可能跨多台机器、子 agent 比父
  agent 活得久——循环（编排层）、pod（机器层）、会话存储流式层分开管理
- **知道何时退到一边**：harness 不消失，但承载内容变化——早期不信任 agent
  每步检查+强制提交；模型变强后把逻辑移进 agent 可控的工具（给它 GitHub
  CLI、告诉仓库布局，让它自己决定）；CI 修复从"harness 抓日志写进 VM"变成
  "让 agent 访问 CLI + 大输出自动写文件供搜索"
- **云端提示要鼓励更自主**：卡住的代价更高——本地 agent 停下等许可你
  知道；云端可能停几小时直到你回去看
- **自愈环境**：缺密钥/网络受阻时主动报告并自愈行动（autoinstall 方向）

> 来源：Cursor《用 Auto-review 管控智能体自主性》《我们在构建云端智能体时
> 学到的经验》。

## 10. 常见失败模式（识别即省时）

| 失败模式 | 症状 | 对策 |
| --- | --- | --- |
| **Kitchen sink 会话** | 一个任务中途穿插无关请求，上下文被污染 | 无关任务之间 `/clear` |
| **反复纠正** | 同一问题纠 2+ 次仍错，上下文堆满失败尝试 | 第 2 次失败后清空重开，带着教训写更好的初始 prompt |
| **过度冗长的 CLAUDE.md/AGENTS.md** | AI 忽略一半规则（重要规则被噪音淹没） | 狠心修剪；AI 已做对的规则删掉或转成 hook |
| **信任-验证缺口** | AI 产出看似合理的实现，边界情况全漏 | 始终提供验证（测试/脚本/截图）；无法验证就别发布 |
| **无限探索** | "调查一下"没限定范围，读了上百文件塞满上下文 | 收窄范围或用子代理，探索不占主上下文 |
| **过早假设** | 没建反馈循环就猜原因，修了表面问题 | 先建"会红"的循环（测试/脚本），再谈假设（见 13-AI 开发协作） |
| **spawn 失控** | 简单查询也派 50 个子代理 | prompt 内嵌"工作量匹配复杂度"规则（见第 7 节） |

> 来源：Anthropic《Best practices》"Avoid common failure patterns"；
> 《Multi-agent》"Scale effort to query complexity"。
